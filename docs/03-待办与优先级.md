# 待办与优先级

> 用途：把"还没做的"一次列清，按依赖和性价比排好，统一开工。
> 判据三条：① 是否依赖硬件　② 是否更贴近真实远动装置　③ 是否容易被追问到。

---

## 一、总览

| 批次 | 内容 | 依赖硬件 | 粗估 | 为什么排这个位置 |
|---|---|---|---|---|
| **A** | 点表改配置 + 动作约束 | ❌ 不依赖 | 1.5 天 | 最便宜、最像真实装置、追问最容易扎这里 |
| **B** | 对时 C_CS_NA_1 + SOE 时标 | ❌ 不依赖 | 1 天 | 补完时间语义，故事完整 |
| **C** | Modbus 南向两个实现 | ✅ 板子到货 | 2 天 | 没有硬件无法验证 |
| **D** | 树莓派 + systemd | ✅ 板子到货 | 1 天 | 部署形态，最后一段 |
| **E** | 杂项：总召唤分组 / 重传 / 死区 | ❌ 不依赖 | 1 天 | 加分项，可延后 |

⭐ **A + B 是当前最该做的**：都不依赖硬件，且都直接提升"被追问三层不崩"。

## 二、批次 A：点表配置化 + 动作约束

### A1. 点表改为配置文件

| 项 | 内容 |
|---|---|
| **现状** | 点表写死在 `scripts/run_slave.py`：`st.add(1, M_ME_NC_1, 23.7)` |
| **目标** | 从配置文件（YAML 或 CSV）读点表；代码不出现任何具体 IOA |
| **字段** | IOA、类型、名称、单位、系数、死区、是否周期上送、遥控绑定（输出通道 / 回读 IOA）、数据源通道、分组号 |
| **验收** | ① 改配置不改代码，点表变化生效　② 非法点表启动即报错，**定位到 `points[i]` + ioa + 字段名**（JSON 语法错误额外给行列号）　③ 现有测试全部通过　④ 默认示例配置的采集行为与改造前等价 |
| **估时** | 1 天 |

⭐ 为什么重要：**真实远动装置的点表是运维改的，不是开发改的。**  
改完之后，"换个现场"就变成"换张表"，这是这类装置的基本形态。

### A2. 遥控动作约束（四条）

| 约束 | 规则 | 否定确认的 COT |
|---|---|---|
| **设备离线** | 目标点品质为 IV（或整个站点无效）时拒绝执行 | 激活确认 + P/N 位 |
| **互斥** | 同一互斥组的输出不能同时为 1（例如"正转/反转"、"开阀/关阀"） | 同上 |
| **最小间隔** | 同一 IOA 两次执行之间不小于配置值（防主站抖动连发） | 同上 |
| **未绑定/不支持** | IOA 不存在或类型不对 → 拒绝（**已实现**） | 同上 |

| 项 | 内容 |
|---|---|
| **验收** | 每条约束一个用例，覆盖"被拒绝时执行器不动作" |
| **估时** | 0.5 天 |

⭐ 为什么重要：现在遥控是"收到就执行"，**没有业务语义**。  
真实装置一定会有前置校验——这是"遥控为什么不生效"的第一现场。

## 三、批次 B：对时 + SOE

### B1. 对时（C_CS_NA_1）

| 项 | 内容 |
|---|---|
| **现状** | 编解码没有该类型；收到后落进"未处理类型"分支 |
| **目标** | 收对时请求 → 记录主站时间与本地时间偏移 → 回激活确认（`COT=7`，回显收到的时标）→ 后续事件时标按偏移校正 |
| **验收** | 主站下发对时后，本地记录偏移量可查；偏差超阈值时打告警日志 |
| **估时** | 0.5 天 |

### B2. SOE：变位改用带时标类型

| 项 | 内容 |
|---|---|
| **现状** | 变位按 `M_SP_NA_1`（无时标）上送 |
| **目标** | 变位按 `M_SP_TB_1`（单点 + CP56Time2a）上送；总召唤仍用无时标类型 |
| **验收** | ① 主站能解出时标　② 连续多次变位时标单调不减　③ 时标精度说明写进文档（见下方边界） |
| **估时** | 0.5 天 |

⚠️ **边界必须写清**：没有硬件对时源时，时标精度只能到"计算机时钟 + 网络往返"量级，**不是毫秒级 SOE**。文档里要明说，不能被追问时改口。

## 四、批次 C：Modbus 南向（板子到货后）

### C1. `ModbusActuator`

| 项 | 内容 |
|---|---|
| **寄存器语义** | 写 `0x0000` 高 8 位（功能码 06，低字节必须 `00`）；写失败的重试与超时 |
| **关键纪律** | **回读必须走独立路径**，不能"写成功就当成功" |
| **验收** | 空载测试：写 `0x0100` → 继电器吸合 → 读回 `0x01xx` |

### C2. `ModbusSource`

| 项 | 内容 |
|---|---|
| **寄存器语义** | 读 `0x0000`（功能码 03，共 1 个寄存器）：高 8 位 = 输出状态，低 8 位 = DI 输入 |
| **纪律** | 读不到 → 不返回该点（上层自动标 IV），**不许塞旧值** |
| **验收** | 拔掉 485 线 → 对应点品质变 IV → 突发上送给主站 |

### C3. 硬件端到端

| 项 | 内容 |
|---|---|
| **链路** | 104 主站 → 子站 → RS485/Modbus → 继电器模块 → 回读 → 104 上送 |
| **验收** | ① 总召唤 4 点正确　② 遥控选择-执行后继电器真实动作　③ 回读一致才判成功　④ 人为断开被控对象时检出失败 |
| **估时** | 合计 2 天 |

## 六点五、⏸ 归档：阻塞于硬件（暂存，不再推动）

以下批次**不是没想清楚，是推不动**——等设备到位后解冻：

| 批次 | 内容 | 阻塞原因 | 解冻条件 |
|---|---|---|---|
| **C** | `ModbusActuator` / `ModbusSource` / 真机端到端 | 继电器模块在途 | 板子到货 + RS485 能通 |
| **D** | 树莓派 + systemd | 板子未到，且树莓派被项目 1 占用 | 项目 1 的 ARM 优化释放设备 |

⭐ **这两批的共同点：协议层一行不用改。**
`actuator.py` / `source.py` 两个接缝已定型，接真机只是**新写两个实现类**，不动 `link.py` / `asdu.py` / `server.py`。

⭐ **另一个共同点：它们对应 `docs/02` 功能验收里的第 2、3、5 条**——
"输出通道真实动作"、"触点回读确认"、"拔电重启自愈"。也就是说，**五条验收里现在还差的就是这三条，而三条都卡在硬件上**。

## 七、明确不做（写进文档的边界，不假装有）
| 不做 | 原因 |
|---|---|
| 冗余（双机热备 / 双通道） | 超出范围，且无法验证 |
| 规约一致性测试认证 | 需送检测机构 |
| 电力二次系统安全防护（纵向加密认证） | 需专用装置 |
| SIL / 功能安全相关 | 本实现不是安全相关设备 |
| 毫秒级 SOE 精度 | 无硬件对时源 |
| 平台层 / Web UI | 本项目不提供人机界面，主站即界面 |
